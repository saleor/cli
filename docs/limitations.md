# Known limitations

- Not installable yet: `pnpm build` produces a standalone `dist/saleor.mjs`, but the package (`bin`, `files`, `private`) is not set up to publish it, and `pnpm saleor` runs the TypeScript sources on Node 22.18+.
- Configurator, backups, restores, upgrades and organization creation are not supported.
- Login uses Jolly's OAuth client (`jolly`) until device login is enabled for `saleor-cli`.
- Browser approval and the OS keyring have not been tested end to end against production.
- New projects use the free plan; choose another plan, and delete projects, in the Saleor Cloud dashboard.
- The CLI does not work out what an environment costs. Before it creates one in a project outside the free plan, it says that you might be charged, depending on your plan.
- Cloud has no idempotency keys: two simultaneous creates with the same name can both succeed.
- A create that fails ambiguously (timeout, 5xx) is not retried; re-run the command to find out whether it happened.
- `--timeout` bounds waiting, not the whole command; API timeouts and retries can add to it.
- Pre-warmed environments (no `--domain-label`) come with whatever database contents Cloud chose; an empty database is not guaranteed.
- Cloud readiness checks the public GraphQL payload; Cloud does not return store credentials. Local setup generates an admin login.
- Concurrent CLI processes writing credentials are last-writer-wins (no file lock).
- `saleor commands` reads an internal Effect API to list arguments and flags; an Effect upgrade can break it (a test catches this).
- Local image downloads and migrations are outside the readiness timeout. Local ports are checked before containers start; a process that claims one after that check is not detected.
- Shell completions list a `--no-<flag>` negation for every boolean flag (including `--no-no-browser`); Effect generates them and offers no opt-out.
- Local stacks have been exercised with Docker, but the Dashboard UI and arbitrary API/Dashboard version combinations have not been reviewed in a browser.
- All modules load at startup; there is no startup-time budget yet.
- The production API omits `login` and `password` from environment responses, which the published schema marks required; the CLI treats them as optional.
- Storefronts follow the template's `main` branch, so a change upstream can change what is downloaded; the CLI warns when the template stops mentioning a key it sets. Only the GraphQL API URL and the default channel are configured: no `SALEOR_APP_TOKEN` (channel discovery, guest order lookup), because `storefront create` does not create store tokens yet.
- Whether a channel exists is checked with the public `channel` query; a store that hides it is reported as not checked.
- A Cloud store's token is made with the Cloud login, as the previous Saleor CLI did: the login goes in the store's `Authorization-Bearer` header to create (or reuse) an app named `Saleor CLI` with every permission the account has, and the app's token is saved for the store. The previous CLI sent a long-lived Cloud API token (`SALEOR_CLOUD_TOKEN` is one); whether stores accept the short-lived token `saleor login` saves has not been checked against production. When a store refuses, the CLI asks for a token as before.
- `webhook listen` creates its app with every permission the token's owner may grant, not only what the events need. If the process is killed (`SIGKILL`) or the machine stops, the app stays on the store: delete apps named `Saleor CLI listener …` in the Dashboard. Only asynchronous events are supported; synchronous webhooks (payments, shipping, taxes) need an app that answers them.
- `webhook listen` has been exercised against a real local store with Docker Desktop on macOS; Linux reaches the listener through `host-gateway`, which is covered only by the compose file. Cloud stores need a tunnel the person runs.
- Local instances made before `webhook listen` refuse to deliver webhooks to this computer (Saleor's private-address filter): the setting is applied when its containers start, so run `env stop` and `env start` on it once.
- `api call` has no pagination helper; page with `--variables` and `pageInfo` yourself.
- There is no app template module yet, so `components` in `saleor.yml` only ever lists storefronts.
- The storefront template's content configuration is found at a fixed path (`config/saleor/storefront-content.config.yml`); the template does not declare it. Its translations script (`configurator:storefront-content:translations`) is not run by `config deploy`.
- Covering several files has been tested end to end through `config validate` only; `config diff`, `deploy` and `status` share its file list but have not run against a store with more than one file. A partial deploy failure stops before the next file.
- A new store gets the project's `config.yml` only, not component content; deploy that with `config deploy <env>`.
- `app add` installs from a manifest URL only: there is no App Store lookup and no link to an app component in the project yet. `app list` shows the first 100 apps. `app reinstall` is a delete and a new install (Saleor has no reinstall), so the app gets a new id and sets up its webhooks and settings again; if the install fails after the delete, the app is gone until `app add` succeeds.
