# Testing the CLI

Run `pnpm check` for lint, type checks, and the source test suite. Run `pnpm test:e2e` to build the standalone CLI and exercise it as a separate Node process against mock servers. The latter is also available as `pnpm test:build`.

GitHub Actions runs checks on pull requests and pushes to `main`. One Linux job on Node 24 runs lint, type checks, the source suite, and the built CLI end-to-end suite. CI uses the locked pnpm version and a frozen lockfile, needs no secrets, and has read-only repository permissions.

## Lint policy

`pnpm lint:code` runs type-aware Oxlint with Ultracite's core and anti-slop presets plus the CLI's Effect rules. Oxfmt handles formatting; Biome is not used. `pnpm lint:fix` applies lint fixes and formatting. The commands target CLI source, scripts, entry points, and tool configs, so generated project storefronts are not scanned.

The maintainability thresholds follow the [MCP lint pilot](https://github.com/saleor/monorepo/pull/189): cognitive complexity 15, cyclomatic complexity 20, nesting depth 3, and at most 3 parameters. Production files are limited to 500 lines and functions to 100, excluding blank lines and comments. At most one class is allowed per file. File/function length and nesting limits do not apply to test fixtures; complexity limits still do.

Type-aware checks reject unsafe values and assertions, unnecessary generics, floating promises (including `void`), and async callbacks used by synchronous APIs. Focused/skipped tests, loose equality assertions, warnings, and unused suppressions fail lint. Test fixtures may construct invalid values; narrowly documented Effect adapter assertions preserve relationships erased by the framework's registration APIs. Compatibility and style overrides live in `oxlint.config.ts`; they do not relax the size or complexity limits.

`pnpm lint:policy` checks 15 deliberately invalid examples against the effective configuration. It runs in `pnpm check`, alongside the existing module-boundary tests that keep core independent of providers and modules independent of siblings.

## What the end-to-end suite covers

`src/main.test.ts` launches the actual CLI entry point with an isolated working directory, configuration directory, file credential store, and an allowlist of environment variables. Each test starts a loopback HTTP server on an ephemeral port. Real Cloud credentials and agent environment markers are not inherited. Every CLI process is killed and fails its test after ten seconds, so a stalled command cannot leave the test runner waiting indefinitely.

- Discovery: help, version, command catalog, argument validation, and explicit `--agent` output.
- Authentication: device grant approval/error responses, pending login recovery, token refresh, private credential persistence, logout, and missing credentials.
- Cloud lifecycle: `init` creating a project and sandbox and then reusing both, `env add` naming a second sandbox in `saleor.yml`, environment listing, readiness polling, previews, and `env remove` deleting a store by its name and forgetting the name. A stateful mock preserves resources between CLI invocations and checks the exact write sequence, so repeated commands must reuse resources instead of creating duplicates.
- Store readiness: a local HTTPS server answers the Saleor `shop` GraphQL query. The test generates a short-lived certificate with OpenSSL and trusts it through `NODE_EXTRA_CA_CERTS`; TLS verification stays enabled. It checks that readiness checks send the store no token.
- Safety and recovery: the billing notice, production deletion refusal, dry runs without writes, explicit resource selection, ambiguous writes, busy tasks, retry suggestions, and resumable timeouts.
- Local commands: `init --local`, `env list`, `env start`, `env stop` and `env remove`, by name and by ref, run against a fake Docker executable and a mock GraphQL API. The test checks retained instance configuration after stopping and distinguishes ordinary shutdown from volume deletion.
- Store API and webhooks (`src/store-commands.test.ts`): `api call` sending documents with the store token, `--anonymous`, files, GraphQL and permission errors, and refusing bad input before contacting the store; `webhook listen` creating a temporary app with the token's permissions, refusing deliveries to other paths, forwarding a delivery with its signature, and deleting the app after `--count`, Ctrl+C or SIGTERM.
- Cloud store tokens: `api call` on a Cloud store over HTTPS sends the Cloud login only as `Authorization-Bearer`, creates the `Saleor CLI` app with the account's permissions, saves its token and reuses it, and makes a new token for the existing app when none is saved; `app add` sends the Cloud login instead, since installing takes a staff user, while `app list` keeps the app token. Local store tokens (`src/store-commands.test.ts`): each command signs in as the admin and saves nothing, `env remove` forgets a saved token, and `webhook listen` signs in again when deleting its app is refused as expired.
- Apps (`src/store-commands.test.ts`): `app add` previewing, installing with the manifest's permissions, a `localhost` app on a local store (the store gets `host.docker.internal`, a project app's `.env` gets its base URLs, an unlisted app pointing at `localhost` is refused), reusing an installed app, retrying a failed installation and reporting one that fails; `app list` with pending installations; App Store apps on a mock Cloud store over HTTPS (`src/main.test.ts`: the catalog without plugins or apps lacking a manifest, one entry per manifest URL, installing by id and name, reuse, the `app-store` source) and refused on a local store; the App Store list (`src/modules/app/store-apps.test.ts`: installed apps start ticked, unticking uninstalls only App Store apps, nothing changes until the plan is applied); `app reinstall` refusing without `--force`, deleting and installing again (the mock, like Saleor, will not read an installed app's manifest), copying the old app's metadata only with `--copy-metadata`, and keeping the app when its manifest cannot be read; `app remove` refusing without `--force`, uninstalling, and succeeding when the app is gone.
- App template (`src/store-commands.test.ts`): `app create` from a local template archive: two apps in one project with their own folders, manifest ids and `saleor.yml` components, `.saleor-app-auth.json` ignored and `.env` uncommitted, reuse keeping the id, and refusing a folder that holds something else.
- Storefronts: `storefront create`, `storefront use` and `init --local --storefront` download a template from a local server, use real git, and check the `.env`, the commit, reuse, backend switching, refusals, missing stores and channel warnings.

The local lifecycle unit suite separately covers fresh initialization, migration failures, credentials, ports and recovery. Core suites cover the shared conventions: `action.test.ts` (confirmation, review after questions, dry runs, absent targets), `target.test.ts` (target resolution and prompts), `lock.test.ts`, `runtime.test.ts` (menus), `env-file.test.ts` and `scaffold.test.ts` (template unpacking, including long paths and entries outside the template), and `conventions.test.ts`, which checks every registered command against the grammar (noun and verb, the verb list, paired verbs, `<env>` as the one way to name a store) and the rules of its kind.

## Boundaries

These tests verify the CLI's process, filesystem, and HTTP behavior against the recorded API contract. They do not start real Saleor containers, validate Docker images or database migrations, exercise browser login approval, or use the OS keyring. They also do not prove that the live Cloud API still matches the fixtures. OpenSSL must be on `PATH` when running the end-to-end suite; it is available on the CI runners.

`pnpm test:live --org <slug>` is a separate, manually invoked smoke test against real services. It is not part of CI. With `--project <slug> --allow-create-delete` it creates a sandbox in that project and deletes it.
